## 常规与项目概览

### Q: Czkawka 与 Krokiet 有什么区别？

两者共享同一个扫描引擎（`czkawka_core`）。区别在于前端：

- **Krokiet** - 当前推荐的 GUI，基于 Slint 框架构建。静态链接，无外部 GUI 依赖，在 Windows、macOS 和 Linux 上均可靠运行。正在积极开发中。
- **Czkawka GTK** - 基于 GTK4 的旧版 GUI。自 v12.0 起已弃用；不再添加新功能，所有开发都在 Krokiet 中进行。GTK 在 Linux 上工作良好，但在 Linux 之外（Windows 和 macOS）存在大量问题 - 透明/不可点击的窗口、HiDPI 显示模糊文字、预览失效、渲染器崩溃 - 其中许多由于 GTK4 Windows/macOS 移植的现状而无法完全修复。Krokiet 正是为了摆脱这些跨平台 GTK 问题而创建的。
- **czkawka_cli** - 用于脚本和自动化的命令行界面。

直接使用 Krokiet - 它是所有平台推荐的前端。

### Q: Czkawka 安全吗？它会访问互联网吗？

Czkawka 和 Krokiet 不会建立任何网络连接。该应用程序没有遥测、没有更新检查，也没有分析。如果你在沙箱分析中观察到网络流量，通常是由分析环境本身引起的。

如果你想自行确认，可以查看仓库中的 `Cargo.lock` - 依赖项中没有网络/HTTP/遥测 crate（没有 `reqwest`、`hyper`、`curl` 等），因此应用程序没有任何代码路径可以访问互联网。

积极维护的下载来源为：
- [GitHub 发布页面](https://github.com/qarmin/czkawka/releases) - 主要的、始终最新的来源
- [crates.io](https://crates.io/)

[Flathub](https://flathub.org/) 包（GTK GUI）仍然存在，但**不再由作者维护，且冻结在 v10.0** - 严重滞后。不存在 Krokiet Flatpak。

诸如 `czkawka.net`、`czkawka.com`、`czawka.net` 等网站**不是官方**且可能不安全。

### Q: 我可以同时运行两个 Czkawka 实例吗？

你可以同时运行不同工具的实例（每个工具有自己的缓存文件）。但是，你**不得**同时运行两个同一工具的实例 - 这样做可能会损坏该工具的缓存。

### Q: 项目许可证是什么？

该项目**不是**统一的 MIT - 它取决于组件，对于 Slint 应用，取决于你是指源代码还是完成的二进制文件：

- **czkawka_core**、**czkawka_cli** 和 **Czkawka GTK GUI** - MIT。
- **Krokiet** 和 **Cedinia** - 它们自己的应用源代码是 MIT（在各自 crate 的 `LICENSE_MIT_CODE` 中），**但作为整体的应用是 GPL-3.0-only**。这是因为它们链接了 Slint UI 框架（根据其免费许可），该框架为 GPL-3.0；因此生成的组合作品/二进制文件必须按照 GPL-3.0 分发（参见 `LICENSE_GPL_APP`）。换句话说：你可以根据 MIT 重用它们的代码，但构建的 Krokiet/Cedinia 是 GPL。
- 所有**图像和音频文件** - CC BY 4.0。

每个 crate 目录中的 `LICENSE_*` 文件包含确切文本。

### Q: 是否有基于网页的 UI 或基于 Docker 的 Web 界面？

有第三方 Docker 镜像由 jlesage 制作，它们将 GUI 包装成可通过浏览器访问的 VNC/web UI：`jlesage/krokiet`（Krokiet）和 `jlesage/czkawka`（GTK GUI）。

### Q: 是否有每日构建/预发布版本？

有。从最新 master 分支提交编译的每日构建版本在 https://github.com/qarmin/czkawka/releases/tag/Nightly 发布。它们可能包含未知错误，但包含在正式发布之前的最新功能和修复。

## 安装与要求

### Q: 系统要求是什么？

- **Linux**：Ubuntu 22.04 或更新版本（glibc 2.35+）。预构建二进制文件是静态链接的（Krokiet）或动态链接 GTK4 的（GTK GUI）。
- **Windows**：Windows 10 或更新版本。Krokiet 二进制文件是自包含的。
- **macOS**：Krokiet 二进制文件提供 Intel (x86_64) 和 Apple Silicon (ARM64) 版本。GTK GUI 二进制文件需要安装 GTK4（例如通过 Homebrew）。

### Q: 如何运行，需要安装什么？（Linux / Windows / macOS）

Krokiet 本身是单个自包含二进制文件 - 下载、运行，即可工作。只有在需要可选功能时才需安装额外的系统库：`ffmpeg` 用于相似视频工具，`libheif`/`libavif`/`libraw` 用于带有这些图像格式功能的构建。（GTK GUI 还需要 GTK4 运行时。）

仓库中有现成的脚本用于安装这些依赖项（`misc/install_scripts/`）：
- `install_linux.sh`（以 `sudo` 运行）- 自动检测 apt / dnf / pacman / zypper 并安装 `ffmpeg` + `gtk4`（基础）和 `libheif`/`libraw`/`libavif`/`dav1d`（可选）。
- `install_macos.sh` - 安装（并提供设置 Homebrew，然后）`ffmpeg libheif libraw libavif` 通过 `brew`。
- `install_windows.bat` - 通过 `winget` 安装 `ffmpeg`；指出 `libheif`/`libraw`/`libavif` 仅可通过 MSYS2 构建获得。

按平台：

- **Linux**：下载 `linux_krokiet_x86_64`（或 `_arm64`），`chmod +x` 它并运行。要使用 HEIF/AVIF/RAW，使用 `heif_raw_avif` 构建并安装匹配的库（或直接运行 `sudo misc/install_scripts/install_linux.sh`）。GTK GUI 需要安装 GTK4。
- **Windows**：下载 `windows_krokiet_on_*` 构建并运行 `.exe` - 核心应用不需要运行时。安装 `ffmpeg`（例如 `winget install Gyan.FFmpeg` 或 `misc/install_scripts/install_windows.bat`）仅在需要相似视频时。
- **macOS**：下载 `mac_krokiet_arm64`（Apple Silicon）或 `mac_krokiet_x86_64`（Intel），然后：

  ```bash
  chmod +x mac_krokiet_arm64
  ./mac_krokiet_arm64
  ```

  如果 macOS 说“无法打开，因为来自分身不明的开发者”，右键点击文件并选择“打开”，然后确认。如果它在 TextEdit 中以文本形式打开，说明未设置可执行位 - 先运行 `chmod +x`。要使用可选编解码器，请使用 `heif_avif` 构建并 `brew install ffmpeg libheif libavif libraw`（或运行 `misc/install_scripts/install_macos.sh`）。GTK GUI（`mac_czkawka_gui_*`）还需要 `brew install gtk4`。

### Q: 哪些 Linux 包可用？

- **预构建二进制文件**：从 GitHub 发布页面下载（推荐，始终保持最新）。这现在是作者积极维护的几乎唯一来源。
- **Flatpak**（GTK GUI，`com.github.qarmin.czkawka`）：曾由作者维护，但**不再更新且停留在 v10.0**。它仍然可用，但严重滞后；希望未来有新维护者接手。不存在 Krokiet Flatpak。
- **AppImage**：**不再提供。** AppImages 已被弃用（特定于 AppImage 的随机错误，相对于普通 Linux 二进制文件价值不大）。使用预构建二进制文件。
- **Snap**：作者**曾发布 Snap 但不再维护**。它已过时并存在已知的权限问题（外部驱动器、NFS）；推荐使用预构建二进制文件。
- **AUR / Debian / 其他发行版仓库**：社区维护，非项目作者。可能落后数个版本。要使用最新版本，请使用 GitHub 二进制文件。

### Q: 相似视频无法工作 - 找不到 ffmpeg

**相似视频**工具需要单独安装 `ffmpeg` 并使其在 `PATH` 中可用。Krokiet 和 czkawka_cli 不捆绑 ffmpeg。

| OS | 安装 |
|----|------|
| Linux | `sudo apt install ffmpeg`（Debian/Ubuntu），`sudo pacman -S ffmpeg`（Arch） |
| macOS | `brew install ffmpeg` |
| Windows | 从 [ffmpeg.org](https://ffmpeg.org/download.html) 安装，并将包含 `ffmpeg.exe` 的文件夹添加到系统 `PATH`。在 Windows 上，也可以将 `ffmpeg.exe` 放在 Krokiet 可执行文件所在的同一文件夹中。 |

安装后，重启 Krokiet 或 CLI。在 Windows 上，PATH 更改生效可能需要新的终端会话（或系统重启）。

## 选择构建版本/二进制文件

发布资产堆叠了几个命名组件，例如 `<os>_<app>[_<features>][_<backend>]_<arch>`。了解下面的图例后，同样的方案适用于每个平台，因此每个操作系统不需要额外学习任何内容。

### 图例

- `krokiet` - 应用程序的主要图形版本，完全支持且正在积极开发，包含新功能和持续改进
- `gtk_gui`（`czkawka_gui`）- 基于 GTK 的旧图形版本，维护模式，仅接收关键修复而不添加新功能
- `cli`（`czkawka_cli`）- 命令行版本
- `cedinia` - 实验性 Android 应用程序
- `arm` / `arm64`、`x86_64` - CPU 架构。大多数 Windows/Linux 机器使用 `x86_64`，而在 Mac 上，`arm`（Apple Silicon）版本正成为最常见的选择
- `heif`、`raw`、`avif` - 需要在操作系统上安装额外库（libheif / libraw / libavif）的额外图像格式功能
- `skia_opengl`、`skia_vulkan`、`femtovg_wgpu`、`all_backends` - 备选 Krokiet 渲染后端；不同构建可能修复某些问题，如模糊字体或图形崩溃。`all_backends` 将所有后端（加上启动脚本）打包在一个包中
- `apk` / `aab` - Cedinia Android 包格式 - 只需使用 `apk`；`aab` 仅用于测试目的
- （仅限 Windows）`on_linux` / `on_windows` - `.exe` 跨平台编译所用的主机

### Q: 应该选择哪一个？

为你的架构选择 `krokiet`，使用**默认**后端 - 它构建得在任何地方都兼容性最好。只有在默认版本出现模糊文字、无法渲染或在 GPU 上崩溃时，才选择 `skia_opengl` / `skia_vulkan` / `femtovg_wgpu` / `all_backends` 构建。只有在需要这些图像格式（并安装匹配系统库）时，才选择 `heif` / `raw` / `avif` 构建。在 Windows 上，如果不确定 `on_linux` 和 `on_windows`，请先从 `windows_krokiet_on_linux` 开始。

### Q: 在 Linux 上 Krokiet 无法显示或渲染错误导致崩溃

尝试设置环境变量并启动：

```bash
SLINT_BACKEND=software krokiet
```

在没有 GPU 的系统（VM、无头服务器）上，这通常是唯一的选择。

默认的 `linux_krokiet_*` 二进制文件只附带 femtovg 和软件渲染器。如果想尝试 Skia/OpenGL/Vulkan/wgpu 后端，请下载 **`linux_krokiet_all_backends_*`** 构建 - 它作为包含二进制文件和小型 bash 启动脚本的 **ZIP** 打包，每个渲染器一个，只设置正确的 `SLINT_BACKEND` 并启动应用程序。因此，你可以直接运行，例如 `./krokiet_winit_skia_opengl.sh`、`./krokiet_winit_skia_vulkan.sh`、`./krokiet_winit_software.sh`、`./krokiet_femtovg_wgpu.sh` 或 `./krokiet_winit_femtovg.sh`，直到找到能正确渲染的一个。

### Q: 哪个 Windows GTK GUI 变体提供？

只提供一个 GTK 构建：`windows_czkawka_gui_gtk_412.zip`（GTK 4.12）。ZIP 还包含 `czkawka_cli.exe` 和小型 `.bat` 启动脚本，用于为 GTK GUI 设置 `GSK_RENDERER`（cairo / opengl / vulkan）。如果 GTK GUI 使用默认渲染器呈现黑窗口或无法启动，请运行这些启动器而不是直接运行 `.exe`，直到找到可用的一个（cairo 是最安全的软件回退）。GTK GUI 已弃用 - 推荐使用不需要 GTK 的 Krokiet。

## GTK 弃用与迁移至 Krokiet

### Q: Czkawka GTK 弹出提示切换到 Krokiet。GTK 真的已弃用吗？

是的。**版本 12.0 是 Czkawka GTK 前端的最后一个发布版本** - 不会再提供新的 GTK 二进制文件，也不会有新功能计划。（任何基于它构建的 Docker 或发行版包都是第三方的，非项目作者维护。）

所有新功能和积极开发都在 **Krokiet** 中进行。用户应迁移到 Krokiet。

### Q: Czkawka GTK 对我有效。为什么要切换？

GTK 前端在 Windows 和 macOS 上存在持续的平台问题，由于 GTK4 Windows/macOS 移植的性质，这些问题无法完全修复。这些问题包括：
- 透明/不可点击窗口（Windows，#1904）
- HiDPI 显示上的文字过小或模糊
- WebP 预览无法工作（Windows，#1095）
- 排序、粘贴文本或使用自定义选择时的各种崩溃（#967，#1170）

Krokiet 使用 Slint 框架避免了所有这些问题，Slint 具有纯 Rust 渲染管道，不依赖 GTK。

### Q: Czkawka 是否支持 Windows 7 或更旧的 Windows 版本？

Windows 10 是最低支持版本。Rust 标准库已停止支持旧版 Windows，因此不支持在 Windows 7 或 Windows XP 上运行，当前版本也不太可能工作。无计划支持那些自身已停止支持多年的系统。Windows 10 可能会继续工作，直到 Rust 本身停止支持，可能大约还 10 年。

### Q: GTK GUI 在我的 4K 显示器上文字太小

对于 GTK GUI：在 Windows 上创建或编辑 `%LocalAppData%\gtk-4.0\gtk.css`，或在 Linux 上创建或编辑 `~/.config/gtk-4.0/gtk.css`，内容为：

```css
* {
    font-size: 22px;
}
```

根据需要调整数值。或者，使用 Krokiet，它支持手动缩放因子。

## Krokiet 渲染问题

### Q: Krokiet 窗口完全黑色/空白/不可见

这通常是 GPU 驱动程序或渲染后端问题。按顺序尝试：

1. **尝试不同的构建/渲染后端。** 默认后端旨在最兼容，但没有单个后端适用于每个系统和 GPU 驱动程序。下载 `all_backends` 构建，通过其每个后端的启动脚本（或自行设置 `SLINT_BACKEND`）启动，直到找到能正确渲染的一个。
2. 强制软件渲染器：`SLINT_BACKEND=software krokiet`（Linux/macOS），或在 Windows 系统环境变量中设置 `SLINT_BACKEND=software` 并重启。在没有 GPU 的机器（VM、无头服务器）上，这通常是唯一的选择。
3. 更新 GPU 驱动程序。

## 缓存与配置文件

### Q: 配置和缓存文件存储在哪里？

| 平台 | 配置 | 缓存 |
|------|------|------|
| Linux | `~/.config/krokiet/` | `~/.cache/czkawka/` |
| macOS | `~/Library/Application Support/pl.Qarmin.Krokiet/` | `~/Library/Caches/pl.Qarmin.Czkawka/` |
| Windows | `%APPDATA%\Qarmin\Krokiet\config\` | `%LOCALAPPDATA%\Qarmin\Czkawka\cache\` |
| Flatpak | `~/.var/app/com.github.qarmin.czkawka/config/czkawka/` | `~/.var/app/com.github.qarmin.czkawka/cache/czkawka/` |

缓存在**所有前端之间共享**（CLI、Krokiet、GTK）。Krokiet 和 GTK GUI 读取并写入相同的缓存文件在 `~/.cache/czkawka/`。

Krokiet 配置文件包括：
- `config_general.json` - 窗口大小、语言、深色/浅色主题、当前预设等。
- `config_preset_N.json`（N = 0-10） - 每个预设的扫描目录和工具设置。有 11 个插槽：10 个用户预设加一个保留预设（“CLI 文件夹”）。
- `config_custom_select_state.json` - 自定义选择对话框的保存状态。

### Q: 缓存有多大？会填满我的磁盘吗？

缓存只存储元数据（哈希值、时间戳、大小），不存储文件内容。一次扫描大型集合（150 TB 的文件）最多可能产生几百 MB 大小的缓存，而不是 TB。

### Q: “删除缓存中过时的结果”是做什么用的？

它删除不再存在于磁盘上的文件的缓存条目。这可以保持缓存精简，并避免未来扫描中使用过时的条目。如果你自上次扫描以来删除了许多文件，并且想加快缓存的加载/保存速度，请定期点击它。

### Q: 我应该删除缓存来解决问题吗？

如果你怀疑缓存损坏（例如，扫描结果看起来错误，或者加载缓存时应用程序崩溃），你可以删除 `~/.cache/czkawka/` 中的缓存文件。下次扫描将从头开始重建缓存，速度会较慢，但可能会修复你的问题。

### Q: 预哈希缓存文件和哈希缓存文件有什么区别？

重复查找器使用两阶段哈希管道：
- **预哈希**：对文件开头和结尾的小块计算的快速部分哈希（当前版本中 - 较旧版本只读取开头）。用于快速排除不可能是重复文件的文件（它们在预哈希上不同）。共享相同大小和预哈希的文件会被提升到完整哈希阶段。
- **完整哈希**：对整个文件内容进行加密强度哈希。仅计算在预哈希阶段存活的文件。

两个阶段有独立的缓存文件。这就是为什么你看到重复查找工具有两个缓存文件。预哈希缓存构建起来便宜得多；完整哈希缓存是权威的去重信号。

### Q: 我可以手动编辑缓存文件来更改文件路径吗（例如，在将文件移动到不同位置后）？

缓存默认存储为二进制 `.bin` 文件。当 `.bin` 文件不存在时，应用程序会回退到加载 `.json` 文件（如果存在）。要启用 JSON 缓存保存，请在 GUI 设置中打开“另保存为 JSON”。然后你可以编辑 JSON 并删除 `.bin` 文件以强制应用程序加载 JSON 版本。

原则上可以直接在 JSON 缓存中更改目录路径，但条目还包含文件大小和修改时间戳，因此任何路径更改都必须与实际文件系统状态保持一致。过时的条目在下次扫描时会被忽略。

## 重复文件 - 未找到预期的重复文件

### Q: Czkawka 未找到我的重复文件，尽管我看得见它们是相同的

最常见的原因是**最小文件大小**设置。在 Krokiet GUI 中，默认最小值为 **16 KB (16 384 字节)**，因此较小的文件被忽略。（CLI 使用每个工具的默认值，对于 `dup`，默认值较低 - 8 192 字节。）要扫描较小的文件：

- **Krokiet**：设置 > 最小文件大小 > 设置为低值（GUI 值以 KB 为单位）。
- **GTK GUI**：“项目配置”选项卡 > “大小（字节）最小” > 设置为 `1`。
- **CLI**：添加 `--minimal-file-size 1` 到命令。

### Q: 我有低于 16 KB 的重复文件 - 为什么默认情况下被排除？

大量用户扫描整个驱动器查找重复文件，在规模较大时，微小文件（几个字节到几 KB - 配置片段、空占位符、许可证头部、图标）常常纯粹巧合地相同，并非有意义的重复文件。显示成千上万这样的匹配项大多只会掩盖用户实际上想查找的较大重复文件，并使结果更难审查。16 KB 的下限使关注点保留在值得采取行动的重复文件上。如果你确实需要较小的文件，如上所示降低最小大小。

### Q: 重复模式在回收站/垃圾桶中找到了文件

**在 GUI 中**，默认情况下不应该发生：默认**排除项目**已在每个平台上涵盖回收站 - Windows 上的 `*:\$RECYCLE.BIN\*`（及其他 Windows 系统目录）和 Linux/macOS 上的 `*/Trash/*` + `*/.Trash-*/*`。因此，默认情况下，即使扫描整个驱动器根目录（`C:\` 或 `/`）也会跳过回收站/垃圾桶。

如果垃圾桶文件仍然出现在 GUI 中，你的**排除项目**字段可能已被清除或编辑，丢失了这些默认值。将它们恢复（或将排除项目重置为默认值） - 例如重新添加：
- Windows：`*:\$RECYCLE.BIN\*`
- Linux/macOS：`*/Trash/*`，`*/.Trash-*/*`

**在 CLI 中**，这些默认值**不会**自动应用 - 你必须使用 `-E` / `--excluded-items` 自行添加排除项。为便于此，有两个宏扩展为 GUI 使用的相同模式：
- `$TRASH` - 仅 OS 垃圾桶/回收站（Linux/macOS 上的 `*/Trash/*,*/.Trash-*/*`，Windows 上的 `*:\$RECYCLE.BIN\*`）。
- `DEFAULT` - 完整的默认 GUI 排除集（垃圾桶加上 `.git`、`node_modules`、缓存、Windows 系统目录等）。

```bash
# 扫描整个驱动器时跳过垃圾桶：
czkawka_cli dup -d / -E '$TRASH'

# 或者应用完整的 GUI 默认排除集：
czkawka_cli dup -d / -E DEFAULT
```

（在 bash/zsh 等 shell 中引用 `$TRASH`，以免被当作变量处理。）

### Q: 扫描在“完整哈希”阶段发现的文件比预期少得多 - 有问题吗？

没有。显示的“分析完整哈希 X/Y 个文件”中的数字仅反映到达完整哈希阶段的文件，而不是扫描的总文件数。大小或预哈希不同的文件不需要完整哈希，因此 Y 可能远小于总文件数。这是预期且正确的行为。

### Q: 扫描似乎在接近末尾时冻结（停止/取消无效）

进度条已基于大小，因此非常大的最后一个文件确实需要一段时间 - 但让它看起来*冻结*的更常见原因是，每个文件的工作（解码、哈希、验证文件）作为一个不可分割的任务运行。应用程序只能在任务*之间*停止，而不能在任务中间停止，因此在处理单个巨大的或慢速解码的文件时，无法中断 - Rust 也无法强制中止它，因为工作通常作为内部进程中的正常函数调用运行，而不是可以简单杀死的单独外部进程。因此，单个有问题的文件可能导致整个扫描看起来卡住且对停止无响应，直到它完成。

对于某些工具，这已通过将大任务分成较小、单独可中断的块来改进 - 这已适用于例如重复查找和相似视频搜索。其他工具可能在当前文件完成前仍会阻塞。

### Q: 符号链接和硬链接在重复扫描中如何处理？

- **符号链接不被跟踪且不被扫描。** 在文件收集期间，符号链接被完全跳过 - 扫描器永远不会将符号链接与其目标进行比较，因此符号链接不会被报告为它所指向文件的“重复”。要扫描符号链接所指向的内容，请将实际目标路径添加为包含目录。
- **硬链接默认被忽略**（“忽略硬链接”/`hide_hard_links` 选项在 Krokiet 和 CLI 中均为开启），因此共享同一 inode 的多个名称只计算一次，而不是相互标记为重复。关闭该选项（CLI `-L` / `--allow-hard-links`）如果你希望将硬链接视为单独文件。

## 相似图像

### Q: 相似图像未找到已知的图像重复

检查这些设置：
1. **最小文件大小**：默认值为 16 KB。此大小以下的图像被跳过。如果需要，降低它。
2. **最大差异（相似度阈值）**：`0` 的值仅匹配有效相同的哈希。Krokiet GUI 默认值为 `10`。允许的范围随哈希大小调整（哈希大小 64 时可达约 40），因此升高它以捕获更松散的近似重复。（CLI 默认值较低 - `5` - 因此如果通过 CLI 扫描，可能需要升高 `-s`。）
3. **哈希算法和哈希大小**：不同的算法捕获不同类型的相似性。Krokiet 中的默认值是哈希大小 16 的 Mean 哈希。如果你错过了重复，尝试 Gradient 或 DoubleGradient，使用哈希大小 32 或 64。
4. 图像格式必须受支持。请参见下一个问题。

### Q: 相似图像支持哪些图像格式？

在所有构建中受支持：JPEG、PNG、BMP、TIFF、WebP、TGA，以及不太常见的 FF（Farbfeld）、QOI、EXR 和 JXL。（这些是相似图像工具实际枚举的扩展名。）

需要可选功能的格式：
- **HEIC/HEIF**：需要带有 `heif` 功能的构建（在 Linux/macOS 上需要 `libheif` 系统库）。
- **AVIF**：需要带有 `libavif` 功能的构建 - 使用 `--features libavif` 编译，或使用名称中包含 `avif` 的二进制变体。
- **RAW**（CR2、NEF、ARW 等）：基本 RAW 支持始终通过纯 Rust `rawler` 库内置，但不涵盖每种格式，也不总是完整支持。可选 `libraw` 功能添加 `libraw` 后端 - 这是行业标准库，支持更大一组 RAW 格式并更完整。因此 RAW 在没有任何特殊构建的情况下即可工作；只有在你的相机格式缺失或解码错误时，才使用 `libraw` 构建。

### Q: 相似图像能否跨不同图像格式查找重复（例如 JPEG vs WebP vs PNG）？

可以。相似图像工具无论文件格式如何都比较像素内容。包含相同视觉内容的 JPEG 和 WebP 将被归为一组，只要你使用的构建支持这两种格式。

### Q: 相似图像能否将灰度图像检测为与其彩色原图相似？

可以 - 目前没有内置选项来排除灰度匹配。所有感知哈希算法（Mean、Gradient、Double Gradient、Blockhash）忽略颜色并在亮度上工作，因此图像的灰度转换将与原图高度相似。如果你想避免灰度误报，必须手动过滤结果或使用后处理脚本。

### Q: 相似图像能否检测水平镜像或旋转的图像？

可以 - 通过**几何不变性**设置（CLI `--geometric-invariance`）。它有三种模式：
- `off`（默认） - 按原样比较图像。
- `mirror-flip` - 还匹配镜像/翻转的变体。
- `mirror-flip-rotate90` - 还匹配 90/180/270 度旋转。

这些模式使匹配更昂贵，因此默认关闭。EXIF 方向始终在此设置之前应用。

### Q: 相似图像中有很多误报（不相关的图像被分组在一起）

降低**最大差异**（相似度阈值）。默认设置 `10` 可能匹配视觉上不同的图像，如果它们共享大面积均匀区域（例如黑色边框、白色背景）。尝试 `4` 或 `5` 以实现更严格的匹配。也尝试**提高哈希大小**（例如 32 或 64）：较大的哈希捕获更多细节，因此不相关图像不太可能冲突 - 代价是对重新编码/大小调整的副本稍微严格一些。

### Q: 哈希算法和哈希大小设置是什么意思？我应该使用哪个？

这些设置控制相似图像中的感知哈希步骤：
- **哈希算法**：将图像转换为短指纹的方式。可用算法有 `Mean`、`Gradient`、`VertGradient`、`DoubleGradient`、`Median` 和 `Blockhash`。`Mean`（Krokiet GUI 默认）最快且最宽松。`Gradient` / `VertGradient` / `DoubleGradient` 对结构差异更敏感。`Median` 对亮度/颜色偏移更稳健。`Blockhash` 是一种不同的方法，可以找到不同的近似重复。
- **哈希大小**：每个维度 8、16、32 或 64 位。较大的值生成更长、更精确的指纹，减少误报，但可能错过重新编码的版本。

实用指导：查找同一图像的重新编码/大小调整副本，从 Mean 哈希 + 大小 16 和 8-10 的“最大差异”开始。要实现更严格的匹配（更少误报），使用 Gradient/Double Gradient 与大小 32，并将最大差异降低到 4-5。

### Q: HEIC 图像未找到

确保你使用包含 `heif` 功能的构建。普通的 `linux_krokiet_all_backends_x86_64` 二进制文件**不**包含 HEIF/AVIF 支持。使用 `heif_raw_avif` 变体（例如 `linux_krokiet_heif_raw_avif_x86_64`）或使用适当的功能标志编译：

```bash
cargo run --bin krokiet --features "winit_femtovg,winit_software,heif,libavif,libraw"
```

## 相似视频与 ffmpeg

### Q: 相似视频如何检测重复视频？

相似视频通过对视频采样帧并计算视觉感知哈希来工作，然后在短时间“窗口”中跨越这些哈希序列进行比较。匹配引擎由项目自己的 `similario_core` crate 提供。`ffmpeg`/`ffprobe` 必须安装用于帧提取。

### Q: 相似视频的主要调优设置是什么？

Krokiet GUI 公开了视觉预设（自定义、近乎相同、相似、电影），这些预设设置了合理的值；底层参数（也在 CLI 中单独公开）包括：

- **最大差异/容差**：两个视频可能有多不同仍然匹配（`0-20`；GUI 默认 `15`，CLI `-t` 默认 `10`）。越低越严格。
- **跳过前置秒数**（`--skip-forward-amount`，默认 `15` 秒）：在开始采样前跳入视频的秒数，以跳过片头/黑色片头（`0-300`；`0` = 不跳过）。
- **扫描持续时间**（`-A`，默认 `10` 秒）：采样以构建签名的视频跨度长度。
- **窗口计数**（默认按预设，`1-20`）：采样的时间窗口数量。更多窗口 = 更准确但更慢。
- **持续时间容差 %**：视频按总持续时间预分组；只有当两个视频的持续时间差异不超过此百分比时才会进行比较。
- **最小匹配窗口分数**（`0.0-1.0`）：调用视频“相同内容”所需的窗口分数。

还有一个可选的**音频指纹**比较（默认关闭，资源密集型），具有自己的相似度/持续时间参数。注意：没有一个设置可以简单地跳过每个视频的开头和结尾，也没有单一“最小视频持续时间”切换 - 非常短的视频被跳过，因为它们无法填充采样窗口。

### Q: 相似视频扫描开始但未找到任何内容，或产生许多误报

相似视频通过采样帧和计算视觉哈希来比较视频。当以下情况时，误报（不相关视频被分组）很常见：
- 容差阈值过高（降低“最大差异”设置）。
- 视频共享常见的片头/片尾序列。
- 视频有异常编码（例如，非常低分辨率、损坏的文件）。

如果扫描**未找到任何内容**（错过了真正的重复），原因通常是采样跨度未能捕获足够的视频内容。多个设置都会影响此情况，因此应一起检查：
- **扫描持续时间**太短 - 采样跨度太小，无法构建可靠签名；增加它。
- **窗口计数**太低 - 更少的时间窗口意味着比较的视频内容更少；提高它。
- **跳过前置秒数**太大 - 可能跳过两个片段共享的唯一内容。
- **最小匹配窗口分数**太高，或**持续时间容差 %** 太低 - 两者都可能在比较前拒绝真正的匹配。
- 容差/**最大差异**太低（更严格）- 提高它。

该算法本质上是启发式的，最适合查找同一源材料的重新编码副本，而不是查找碰巧有几个相似场景的视频。

### Q: 相似视频缓存 - 是否在扫描之间复用？

是的，视频哈希缓存存储在 `~/.cache/czkawka/`，并在后续扫描中复用。每个视频只处理一次；后续扫描从缓存中加载预计算的哈希。

注意：缓存按视频**处理**参数（影响每个视频如何被采样和哈希的设置 - 扫描持续时间、窗口计数、跳过前置秒数等）键入。更改任何这些参数会使应用程序使用**不同**的缓存文件，因为计算的哈希值会不同。因此，更改处理参数后，你必须重新扫描，该扫描将从头开始重新处理视频。仅影响已计算哈希如何**分组**为相似视频列表的参数（例如最大差异/最小匹配窗口）不会使缓存失效。

## 参考路径/参考文件夹

### Q: 什么是参考文件夹/参考路径？

参考文件夹是添加到扫描但受到删除或修改保护的目录。参考文件夹中的文件仅出现在结果中用于比较 - 它们显示与哪个“保留”候选项匹配。参考文件夹之外的文件可以正常选择和删除。

典型用例：将你主要、已组织良好的集合文件夹（例如精心策划的照片或音乐库）添加为参考文件夹，将下载文件夹添加为常规包含路径，然后扫描。仅下载文件夹中的文件可选择删除；你主集合中的文件始终被保留。

### Q: 如何从一个文件夹中删除重复文件，同时保留另一个文件夹中的副本？

使用参考文件夹。将要保护的文件夹添加为参考文件夹（在目录列表中旁边勾选“参考”复选框）。扫描后，仅参考文件夹之外的文件显示为可选择。使用“全部选择”然后删除 - 这仅会删除非参考副本。

### Q: 设置参考文件夹后，仅在非参考文件夹中有重复的组仍然会出现吗？

不会。当设置参考文件夹时，仅包含至少一个来自参考文件夹的文件的组会显示。完全在非参考目录中的组被隐藏。这是故意为之：参考文件夹标记“原件”，因此仅当至少有一个原件存在时，组才有意义。

### Q: 如何在 CLI 中使用参考文件夹？

使用 `-r` / `--reference-directories` 标志。要指定多个参考目录，重复该标志：

```bash
czkawka_cli dup -d /path/to/search -r /path/to/ref1 -r /path/to/ref2 -D AEO
```

在单个 `-r` 标志中使用逗号或分号分隔的值**不**有效。每个参考目录必须是单独的 `-r` 标志。

## 删除、移动、硬链接文件

### Q: 删除无效 / “已删除 0 个项目，无法移除 1 个项目”

常见原因：
1. **Samba/NFS 共享上的垃圾桶**：Krokiet 提供两个独立操作 - 永久**删除**按钮和**移动到垃圾桶**按钮（CLI 默认永久删除，使用 `-y`/`--move-to-trash` 可选择移动到垃圾桶）。在网络共享（SMB、NFS）上，移动到垃圾桶路径可能失败，因为远程文件系统没有可用的垃圾桶位置。**修复**：使用永久**删除**按钮（或在 CLI 中省略 `-y`）而不是移动到垃圾桶。
2. **只读文件/文件夹**：文件本身可能可写，但其父目录可能只读。检查包含文件夹的权限。

### Q: 移动很慢 - 它复制整个文件而不是仅重命名

在同一文件系统上，Krokiet 执行重命名（瞬间完成）。如果源和目标在不同文件系统上（例如，从一个驱动器移动到另一个驱动器），则执行完整的复制-然后-删除，预期会很慢。这不是错误。

### Q: Flatpak 版本将删除的文件移动到与系统使用的不同垃圾桶文件夹

这是 Flatpak 沙箱的已知行为。在 Flatpak 容器内移动到垃圾桶的文件进入 `~/.Trash-<uid>/` 而不是 `~/.local/share/Trash/`。这无法配置，是 Flatpak 沙箱的限制，而非 Czkawka 本身的问题。

### Q: 硬链接如何工作？它实际上对我的文件做什么？

硬链接将选定的重复文件替换为指向一个保留副本的硬链接。硬链接后，所有文件共享相同的 inode - 它们显示为独立的文件名，但磁盘空间仅占用一次。**注意**：在不同文件系统或分区上无法进行硬链接。这样的对不会被静默跳过 - 操作会为它失败并报告错误（例如“无法硬链接 ...：无效的跨设备链接”）；原始文件保持完整，因此不会丢失任何内容。

### Q: 一次硬链接多个组时，来自不同组的文件会被链接在一起吗？

不会。每个组独立处理。在组 A 中，未选中的文件成为“原件”，选中的文件成为指向它的硬链接。组 B 中也独立发生同样的情况。来自不同组的文件永远不会被链接在一起。

## 选择与“自定义选择”

### Q: “自定义选择”无效 / 未选择任何内容

“自定义选择”对话框基于文本模式选择文件，该模式与文件名、路径或正则表达式匹配。常见错误：
- 模式必须匹配完整路径的子字符串。使用 `*` 作为通配符。
- 在 Windows 上，在模式中使用正斜杠或转义反斜杠；模式中的反斜杠可能行为出乎意料。
- “不要选择组内的所有文件”复选框：如果勾选，每个组中始终至少保留一个文件未选中（一种安全措施，以避免删除所有副本）。如果你想选择所有匹配项，请取消勾选。

### Q: 如何选择特定文件夹之外的所有文件？

1. 使用“自定义选择”并输入要保留的文件夹路径（选择该文件夹中的文件）。
2. 然后使用“反转选择”来交换选择。

或者，将要保留的文件夹设置为**参考文件夹** - 参考文件夹中的文件永远不会被任何自动选择模式选中。

### Q: 如果我点击“全部选择”然后删除，是否会删除文件的所有副本，包括最后一个？

不会。自动选择模式（“全部选择除最新/最旧”等）始终在每个组中至少保留一个文件未选中。普通“全部选择”按钮选择每个选中的行，但每个组的标题行（第一个条目）始终被自动模式保持未选中。如果你手动勾选每一行，可以选择组中的所有文件 - 但即使如此，删除操作在继续前也会警告你。

在 CLI 中，使用 `-D AEN` / `-D AEO` 等时，删除方式由其名称描述：“全部选择除最新”始终每组保留恰好一个文件。

### Q: 我可以使用“自定义选择”按扩展名选择文件吗？

可以。在“正则表达式路径 + 名称”字段中，输入匹配扩展名的正则表达式。例如，选择所有 `.mp3` 文件：

```
.*mp3
```

或者用于 `.flac` 文件：

```
.*\.flac$
```

### Q: Windows 上“自定义选择”的“路径”筛选器未选择任何内容

在 Windows 上，使用不带尾随反斜杠或通配符的纯路径前缀。例如，输入 `C:\Users\username\Desktop`（而不是 `C:\Users\username\Desktop\*`）。筛选器匹配任何其路径包含所输入字符串作为子字符串的文件。

## 错误扩展名工具

### Q: 错误扩展名说我的文件扩展名不对。如何重命名？

在 **Krokiet** 中：在结果列表中选择文件，并使用**重命名**按钮（或右键点击 > 重命名）。建议的新扩展名在“额外”列中显示（`当前扩展名 -> 正确扩展名`）。

在 **CLI** 中：传递 `-F` / `--fix-extensions` 到 `bad-ext`，匹配的文件将自动重命名为使用检测到的正确扩展名：

```bash
czkawka_cli bad-ext -d /path/to/scan -F
```

在 **GTK GUI** 中：不支持从 GUI 重命名。导出结果并手动重命名。

### Q: 错误扩展名错误地标记了文件的扩展名，或犯了其他明显错误

扩展名检测使用文件魔数（`infer` crate）。许多文件格式共享相同的开头字节，因此无法仅从内容中无歧义地选择单个“正确”扩展名。示例：
- 基于 ZIP 的格式（`.zip`、`.docx`、`.xlsx`、`.pptx`、`.jar`、`.apk`、`.epub`）都以相同的 ZIP 签名开头。
- 旧版 Microsoft Office 格式（`.doc`、`.xls`、`.ppt`）是复合二进制文件，共享相同的 OLE 容器头部。

在这些情况下，该工具只能报告它检测到的文件系列，而不能指出哪个特定扩展名是“对”的。一些不常见的格式也可能从库的数据库中缺失。如果需要，可以从扫描中排除特定扩展名。

## 扫描外部驱动器、NAS、网络路径

### Q: 如何排除隐藏/系统目录，如 Synology 的 @eadir 或 macOS .DS_Store 目录？

使用**排除项目**字段（不是排除目录）。添加与路径中任意位置的目录名匹配的通配符模式。示例：

- Synology `@eadir`：`*/@ea*`
- macOS `.Spotlight-V100`、`.fseventsd` 等：`*/.Spotlight*`，`*/.fseventsd*`
- 任何以 `.` 开头的隐藏目录：使用排除目录添加特定路径。

排除项目模式使用 `*` 作为通配符，并与每个文件/目录的完整路径匹配。

### Q: 无法使用 Krokiet 在 Windows 上扫描 Windows 网络共享（SMB 路径）

在 Windows 上，UNC 路径如 `\\server\share\` 可能在文件选择器对话框中不显示。使用目录面板中的“手动添加”文本输入直接输入或粘贴 UNC 路径。

如果仍有麻烦，将共享映射到驱动器字母（例如 `net use Z: \\server\share` 或资源管理器 > “映射网络驱动器”），然后扫描结果的 `Z:\` 路径 - 常规驱动器字母比原始 UNC 路径行为更可预测。

### Q: Czkawka / Krokiet 无法访问 `C:\System Volume Information` - 拒绝访问

这是预期行为。系统目录和 Windows 保留的卷无法被普通用户进程访问。Czkawka 记录访问错误，但继续扫描目录树的其余部分。这些错误无害。

### Q: 我可以在 Krokiet 中使用拖放来添加目录吗？

目前不行。拖放添加目录尚未实现，因为 Slint（Krokiet 使用的 UI 框架）尚未公开拖放支持。一旦 Slint 添加，就可以在 Krokiet 中实现。目前，使用“添加”按钮或在文本字段中输入/粘贴路径。

## 性能与大型扫描

### Q: 传统 HDD 上扫描速度很慢

HDD 上的扫描速度受寻道时间限制。应用程序收集文件元数据，并在读取前按 inode 号排序文件，这改善了顺序读取模式。然而，对于非常大的目录，性能仍将远低于 SSD。

提示：
- 启用**缓存**（默认启用）。对同一文件的第二次扫描快得多。
- 启用**预哈希**（Krokiet 中默认启用）。这添加了一个快速的部分哈希阶段，在完整哈希之前消除大多数非重复项。
- 将扫描限制在特定子目录，而不是一次扫描整个多 TB 驱动器。
- 有可能限制一次从磁盘读取的线程数，但实际上这帮助不大：文件数据已经以相当大的块读取（一次 1-2 MB），因此线程不会产生限制线程数可以平滑处理的那种微小随机读取。

### Q: 扫描成千上万个组后，UI 变得非常缓慢/卡顿

在 Krokiet 本身中，这种情况不应该发生 - 结果列表是虚拟化的，Krokiet 可以无任何问题呈现数百万条目。唯一可能真正变慢的地方是底部文本/输出面板：当它积累了非常大量的文本时，呈现该文本会变慢。这是 Slint 文本呈现错误，而非结果列表的问题。作为一种变通方法，折叠或隐藏底部面板。

### Q: 在大型相似图像或相似视频扫描期间，CPU 使用率急剧升高 - 这是预期的吗？

是的。不同的阶段压力不同：有些步骤是高度 CPU 绑定的（感知哈希/解码工作，并行于所有核心，导致 CPU 使用率飙升），而另一些主要是磁盘绑定的（读取文件内容）。这是正常的。如果你想降低 CPU 使用率，可以限制线程数量（CLI `-T <N>` / `--thread-number`，或 GUI 中的线程设置）。

## CLI 用法

### Q: 如何使用 CLI 扫描多个目录？

为每个目录重复 `-d` / `--directories` 标志。**不要**在单个标志中将路径用空格或逗号分隔：

```bash
# 正确：
czkawka_cli dup -d /path/to/dir1 -d /path/to/dir2

# 错误（将失败）：
czkawka_cli dup -d /path/to/dir1 /path/to/dir2
```

### Q: 如何通过 CLI 删除重复文件？

使用 `-D` 标志和删除策略。示例 - 保留最旧的副本，删除所有其他：

```bash
czkawka_cli dup -d /path -D AEO
```

可用策略：`AEN`（全部选择除最新），`AEO`（全部选择除最旧），`ON`（仅最新），`OO`（仅最旧），`AEB`（全部选择除最大），`AES`（全部选择除最小），`OB`（仅最大），`OS`（仅最小），`HARD`（替换为硬链接）。

添加 `--dry-run` 以预览将要删除的内容而不实际删除任何内容。

### Q: CLI `--allowed-extensions` 似乎排除了扩展名而不是包含它们

这是旧版本中的一个错误（过滤器逻辑被反转）。已在最新版本中修复。更新到最新版本。

### Q: 如何将结果保存到文件？

使用 `-f` / `--file-to-save` 标志用于纯文本输出，或 `-C` 用于紧凑 JSON，或 `-p` 用于美观打印的 JSON：

```bash
czkawka_cli dup -d /path -f results.txt          # 纯文本
czkawka_cli dup -d /path -C results.json         # 紧凑 JSON
czkawka_cli dup -d /path -p results_pretty.json  # 美观打印的 JSON
```

### Q: CLI 是否有进度显示？

CLI 不显示实时进度条（当前版本中没有旋转器/百分比）。它在扫描过程中打印高级阶段转换，但没有实时每个文件进度计数器。

### Q: 如何静默运行 CLI / 抑制输出？

使用 `--do-not-print-results`（`-N`）抑制结果列表，并使用 `--do-not-print-messages`（`-M`）抑制所有信息性消息和警告。两者可以组合。

### Q: 如何限制 CLI 使用的线程数量？

使用 `-T <N>` / `--thread-number <N>`。设置 `0`（默认）使用所有可用的 CPU 线程。

### Q: 如何在 CLI 中按扩展名排除文件？

使用 `-P <ext>` / `--excluded-extensions <ext>` 排除特定扩展名。使用 `-x <ext>` / `--allowed-extensions <ext>` 仅扫描特定扩展名。`--allowed-extensions` 标志也接受宏：`IMAGE`、`VIDEO`、`MUSIC`、`TEXT`。

### Q: 如何在 CLI 中排除路径/项目，它是否与 GUI 相同的垃圾桶默认值？

使用 `-E <pattern>` / `--excluded-items <pattern>` 带有通配符（例如 `-E '*/temp*'`）。与 GUI 不同，CLI **不**自动应用任何默认排除项。两个宏展开为 GUI 默认使用的相同模式：
- `$TRASH` - 仅 OS 垃圾桶/回收站（Linux/macOS 上的 `*/Trash/*,*/.Trash-*/*`，Windows 上的 `*:\$RECYCLE.BIN\*`）。
- `DEFAULT` - 完整的默认 GUI 排除集（垃圾桶加上 `.git`、`node_modules`、缓存、Windows 系统目录等）。

```bash
czkawka_cli dup -d / -E '$TRASH'     # 跳过垃圾桶/回收站
czkawka_cli dup -d / -E DEFAULT      # 应用所有 GUI 默认排除项
```

引用 `$TRASH`，以免你的 shell 将其展开为变量。

### Q: CLI 中是否有干运行模式？

有。添加 `--dry-run` 以预览将要删除的内容而不实际删除任何内容。请注意，干运行输出目前仅发送到控制台，不写入结果文件。

## 安全 - 杀毒软件误报

### Q: Windows Defender / 杀毒软件将 Krokiet 检测为恶意软件

这是一个影响使用链接时优化（LTO）编译的 Rust 二进制文件的已知误报。该二进制文件从开源代码通过公共 CI（GitHub Actions）构建，SHA256 校验和与 CI 工件匹配。

1. 检查文件的 [VirusTotal 扫描](https://www.virustotal.com/) - 几乎所有引擎都应报告干净。
2. 将下载的二进制文件的 SHA256 哈希与 GitHub Actions CI 工件验证。

要解决 Defender 阻止：允许文件在 Windows Defender 中，点击“更多信息 > 尽管如此运行”，或在 Defender 设置中为二进制文件添加排除项。

如果你的杀毒软件继续标记它，请将文件作为误报报告给你的杀毒软件供应商。

## 常见错误消息

### Q: “无法打开目录 /home/user/.ssh，原因：权限被拒绝（操作系统错误 13）”

这是正常的。Czkawka 尝试扫描包含路径下的所有目录。某些系统目录（`.ssh`、`/proc`、`/sys`、`/dev`）对普通用户不可读。这些错误被记录，扫描继续。要抑制它们，将这些目录添加到排除路径中。

如果你确实需要扫描这样的位置，先检查你自己的对其权限（所有权和模式），最后再以管理员/root 身份运行应用程序 - 但扫描整个系统作为 root 很少是你实际想要的，它允许工具操作普通用户无法操作的文件。

### Q: “垃圾桶操作期间出错” / 文件未移动到垃圾桶

通常意味着垃圾桶位于与文件不同的文件系统上（例如，文件在网络共享或没有 `.Trash-<uid>` 目录的次要驱动器上）。解决方案：
- 使用永久删除而不是移动到垃圾桶。
- 对于网络共享（NFS、SMB），永久删除是唯一可靠的选项。

### Q: 损坏文件扫描中出现“损坏的流：mp3 无效的 main_data 偏移量”

此消息来自 `symphonia` 解码库，它严格检查比特流：它报告 MP3 头部包含指向比特流之外的 `main_data_begin` 值。`symphonia` 相当严苛，即使这些问题无害也会标记 - 许多 MP3 文件由于编码器特性而带有这个“错误”，大多数媒体播放器（很可能你自己的播放器）都能正常解码和播放它们。文件仍然可播放；你可以忽略此结果或保留文件。

### Q: 应用程序显示 `.fuse_hidden...` 文件

这些文件由操作系统 / 基于 FUSE 的文件系统自动创建 - 这不是 Czkawka 或 Krokiet 的行为。当另一个应用程序中仍然打开的文件被“删除”时，FUSE 将其重命名为隐藏的 `.fuse_hidden...` 名称，并且只有在最后一个句柄关闭后才真正删除它。它们不是通常意义上的重复文件。你可以通过将 `*/.fuse_hidden*` 添加到排除项目列表来排除它们。

## 便携式/自定义数据路径

### Q: 我可以让 Krokiet 将其配置和缓存存储在自定义位置（便携模式）吗？

可以。在启动应用程序之前设置以下环境变量：

- `CZKAWKA_CACHE_PATH` - 存储缓存文件的路径
- `CZKAWKA_CONFIG_PATH` - 存储配置文件的路径

这些变量由 `czkawka_core` 读取，因此适用于所有前端（CLI、GTK GUI 和 Krokiet）。

示例（Windows）：
```bat
set CZKAWKA_CACHE_PATH=D:\czkawka\cache
set CZKAWKA_CONFIG_PATH=D:\czkawka\config
krokiet.exe
```

示例（Linux/macOS）：
```bash
CZKAWKA_CACHE_PATH=/opt/czkawka/cache CZKAWKA_CONFIG_PATH=/opt/czkawka/config krokiet
```

## 硬链接行为与安全性

### Q: 我意外硬链接了系统或应用程序 DLL 文件。如何撤销？

硬链接系统文件可能导致不稳定，因为对一个硬链接文件的更改会影响所有指向相同 inode 的名称。要撤销硬链接，你需要复制每个文件以断开链接：

在 Windows 上（PowerShell）：
```powershell
# 对于每个受影响的文件：
Copy-Item "C:\path\to\file.dll" "C:\path\to\file.dll.bak"
Remove-Item "C:\path\to\file.dll"
Rename-Item "C:\path\to\file.dll.bak" "file.dll"
```

在 Linux/macOS 上：
```bash
# cp --remove-destination 创建一个新的独立副本
cp --remove-destination original.so original.so
```

为了将来防止这种情况：在扫描前，始终将系统目录（`C:\Windows`、`/usr`、`/lib` 等）添加到排除目录列表中。

### Q: “隐藏硬链接”在扫描设置中是否会防止已经硬链接的文件出现在结果中？

是的。当启用“忽略相同 inode”（或“隐藏硬链接”）时，共享相同 inode 号的文件被视为单个逻辑文件，结果中只显示一个代表。这防止已经硬链接的文件被标记为重复。

## 符号链接处理

### Q: Czkawka 在扫描时是否跟随符号链接？

默认情况下，Czkawka **不**跟随符号链接。符号链接被视为其自身的文件系统条目；扫描不会遍历到符号链接目标。这可以防止当符号链接指向它们时意外删除原始文件。

如果你想扫描符号链接目录的内容，请将目标路径直接添加为包含目录，而不是符号链接。

### Q: 如果我用 Czkawka 创建符号链接，它会删除原始文件吗？

当你使用“符号链接”操作时，Czkawka 将选定的重复文件替换为指向组中第一个未选中的文件的符号链接。原始文件（未选中的）保持完整。选定的文件被原地替换；它们的目录项变成了符号链接。

在 Windows 上，创建符号链接需要提升的权限或启用开发者模式。

## 扫描手机/安卓设备

### Q: Czkawka 能扫描已连接手机（MTP）上的文件吗？

不能。Czkawka 通过标准文件系统 API 读取文件。MTP（媒体传输协议，安卓手机使用）不是真正的文件系统，在 Windows 或 Linux 上无法通过普通文件路径访问。要扫描手机内容，请：
- 使用创建本地文件系统挂载的工具挂载手机的存储（例如，Linux 上的 `jmtpfs`）。
- 将文件复制到本地驱动器，扫描，然后根据结果操作。

### Q: Czkawka 能在安卓上运行吗？

不正式支持。`czkawka_core` 是平台独立的，可以编译为安卓，但没有官方的安卓应用。社区成员已成功在 arm64 设备上使用 Termux（使用 termux-x11 或 SSH X 转发）运行 Krokiet，但这是不支持的，且需要手动编译。请参阅讨论 #1073 了解社区笔记。

## 保存与加载扫描结果

### Q: 我可以保存扫描结果以便稍后审查而不重新扫描吗？

你可以使用 GUI 中的“保存”按钮或 CLI 中的 `-f` / `-C` / `-p` 标志将结果导出到文件。这些文件可以在外部审查。但是，你不能将它们加载回 GUI 以继续你之前的工作 - 应用程序必须重新运行扫描以交互式显示结果。

### Q: 我可以将结果导出为 JSON 用于我自己的脚本吗？

可以。在 CLI 中使用 `-C <filename>` 导出紧凑 JSON，或使用 `-p <filename>` 导出美观打印的 JSON。在 GUI 中，在设置中启用“另保存为 JSON”并使用保存按钮。JSON 格式包含文件路径、大小、修改日期和哈希值（针对重复文件）。

## 重复检测的内部工作原理

### Q: Czkawka 仅使用哈希值，还是进行完整的逐字节比较以确认重复文件？

Czkawka 仅使用哈希值（大小 + 预哈希 + 完整哈希管道） - 不进行逐字节比较。这是可靠的：候选项首先按确切文件大小分组，且仅比较相同大小的文件，因此每次比较涉及的哈希空间很小。冲突需要两个*相同大小*的不同文件也产生相同的完整哈希值，这在默认的 Blake3（一种加密哈希）中实际上永远不会发生。逐字节遍历只会证实哈希值已经建立的内容，但速度慢得多，因此故意不执行。

### Q: 重复查找器使用什么哈希算法？

默认哈希算法是 **Blake3**（非常快，加密强度高）。其他两个选项是 **CRC32**（快速校验和，非加密）和 **XXH3**（xxHash，非常快，非加密）。没有 SHA-256/SHA-512 选项。对于去重，三者在实际中都可以；Blake3 是推荐的默认值，因为它结合了高速和加密级别的抗冲突性。

### Q: 重复查找器如何处理仅名称不同但其他方面相同的文件？

名称不同但内容相同（相同大小和相同哈希）的两个文件被报告为重复。当使用“哈希”检查方法时，文件名不是重复比较的一部分。如果你想仅按名称查找重复，请使用“名称”检查方法。
